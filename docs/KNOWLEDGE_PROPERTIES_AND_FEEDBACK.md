# Свойства, представления и реальные поисковые вопросы

## Свойства wiki

На главной wiki откройте «Свойства и сохранённые представления», примените фильтры и выберите «Свойства» у статьи. Доступны тип (заметка, решение, инструкция, сервис, исследование), статус проверки, ответственный и дата пересмотра. Пустое значение означает, что свойство не задано. Статус «Проверено» устанавливает человек; он не отменяет проверку актуальности источников.

Сохранение проверяет ревизию статьи. При конфликте правки остаются в форме. Меняются только свойства в metadata и ревизия; содержимое, provenance и время обновления содержимого сохраняются. Поэтому изменение ответственного не делает устаревшую статью свежей. Свойства входят в существующий журнал синхронизации документов.

Сохранённое представление хранит фильтры, а не список документов: при открытии состав вычисляется заново. Доступны фильтры по названию/URI, проекту, типу, статусу, ответственному и дате пересмотра включительно. Фильтр даты исключает статьи без даты. Страницы выдаются по 50 записей; допускается до 500 сохранённых представлений. Повторное сохранение выбранного представления проверяет его ревизию; «Сохранить копию» создаёт отдельное.

API:

- `GET /v1/knowledge?q=&wing=&document_type=&review_status=&owner=&due_before=&offset=0` — роль read.
- `PUT /v1/knowledge` — роль write; `{id, revision, properties: {document_type, review_status, owner, review_due}}`.
- `GET /v1/knowledge/views` — роль read.
- `POST /v1/knowledge/views` — роль write; `{name, filters}` для создания, с `id` и `revision` для обновления.

## Реальные вопросы

После поиска раскройте «Сохранить этот вопрос для оценки поиска», отметьте правильные документы или укажите URI/ID правильных источников, которые не попали в выдачу. Для вопроса без подтверждённого ответа в корпусе есть отдельная отметка. Текст вопроса и параметры сохраняются **только после явного нажатия кнопки**. Обычный поиск не начинает журналировать вопросы.

В разделе «Оценка» откройте реальные вопросы, загрузите список и запустите повторную проверку. Используются сохранённые настройки поиска и текущий корпус. Повтор одного запроса сохранения с тем же UUID не создаёт дубликат.

Для положительных примеров показываются recall по указанным документам и MRR. Это неполная человеческая разметка: другие полезные документы могут быть не отмечены. Для отрицательных примеров показывается лишь факт пустой выдачи, без положительного recall/MRR. Это не проверка достоверности сгенерированного ответа.

Хеши правильных источников проверяются до и после прогона. Если источник изменился или исчез, метрики не выдаются: нужна новая разметка. Остальная часть корпуса может изменяться; это не замороженный benchmark. Результат прогона отображается в текущем экране, но пока не сохраняется как история сравнения запусков.

API (чтение — read, сохранение и запуск — write):

- `GET /v1/eval/feedback?offset=0` — по 50 вопросов.
- `POST /v1/eval/feedback` — `{id: UUID, search: параметры /v1/search, expected: [ID или URI], no_answer: false}`. Для отрицательного примера `expected: []`, `no_answer: true`.
- `POST /v1/eval/feedback/run` — `{id: UUID}`.

## Хранение и ограничения

Schema 13 добавляет `search_feedback` и `knowledge_views`. Эти два списка локальны для gateway; они сохраняются в полной резервной копии DuckDB, но не реплицируются как wiki-документы. Удаление записей и экспорт отдельного набора вопросов пока не имеют интерфейса. Новые экраны доступны в веб-клиенте.

Набор `repository-v1` остаётся отдельным набором подготовленных по репозиторию вопросов. Он не становится набором реальных пользовательских вопросов после появления этой функции. Для оценки реального использования нужны вопросы пользователя и проверенные ожидаемые источники.
