# HTTP и MCP: аутентификация и права

HTTP API и `/mcp` используют общую проверку `Authorization: Bearer <token>`.
Права проверяются до выполнения обработчика или MCP-инструмента. Настройка
токенов применяется при запуске процесса; она не меняет содержимое DuckDB.

## Режимы запуска

| Настройка gateway | Поведение |
|---|---|
| Ни один `RAG_HTTP_*_TOKEN` не задан | Разрешён только loopback bind. Локальный клиент получает административные права в пределах включённого API/tool surface. |
| Задан хотя бы один токен | Bearer обязателен для HTTP и MCP, включая loopback, `/health`, `/live` и `/ready`. |
| Non-loopback bind | Нужны и `RAG_HTTP_ALLOW_REMOTE=true`, и хотя бы один корректный токен. Без них запуск отклоняется до открытия Store. |
| Exclusive stdio MCP | Доверенный локальный транспорт с прежними правами; HTTP-токены не ограничивают stdio. Правило одного владельца DuckDB сохраняется. |

Используй только нужные роли. Токены разных ролей должны различаться; пустая
строка не отключает роль и считается ошибкой конфигурации. Чтобы убрать роль,
удали соответствующую переменную из окружения сервиса.

| Переменная gateway | Роль |
|---|---|
| `RAG_HTTP_READ_TOKEN` | Чтение |
| `RAG_HTTP_WRITE_TOKEN` | Чтение и редактирование |
| `RAG_HTTP_ADMIN_TOKEN` | Чтение, редактирование и административные операции |

Каждый токен должен содержать 32–4096 символов случайного Bearer-токена без
пробелов. Поддерживаются `A-Z`, `a-z`, `0-9`, `-`, `.`, `_`, `~`, `+`, `/` и
`=` только в конце. Удобный совместимый формат — случайная hex-строка,
сгенерированная менеджером секретов или криптографическим генератором.
Готовых общих паролей и автоматически назначаемого токена нет.

## Что разрешено ролям

Права действуют на весь corpus gateway: это роли операций, а не изоляция
пользователей, проектов или `wing`. Один и тот же токен роли может использоваться
несколькими клиентами; отдельных учётных записей, OAuth и выдачи токенов API нет.

| Минимальная роль | HTTP | Примеры MCP |
|---|---|---|
| Read | Каталоги, документы, граф, диагностика, история и статусы jobs/sync; `POST /v1/search`, `/v1/pack-context`, `/v1/multi-get` | `search`, `get_document`, `get_wiki_page`, `query_with_index`, `get_neighbors`, `doctor` |
| Write | `POST /v1/wiki` (только создание), `PUT /v1/wiki`, `POST /v1/revisions/restore` | ingest, wiki/schema/diary/log edits, связи графа, metadata/lifecycle edits |
| Admin | Запуск/отмена sync jobs, checkpoint, backup; sync register/push/pull/ack | `sync_sources`, `delete_by_source`, `doctor_repair`, `reembed_document`, `rebuild_index`, `maintain_*`, `refresh_stale_wiki`, backup/import/export |

`get_schema` требует Write: по умолчанию он создаёт schema document, если его
ещё нет. `analyze_corpus` и `plan_maintenance` тоже требуют Write, поскольку
могут записывать ops log. Экспорт графа записывает файл и требует Admin.
Preview/dry-run не понижает требуемую роль. Read допускает обслуживание
производных поисковых индексов и техническую телеметрию; это не режим
DuckDB read-only.

Точный перечень MCP — [`src/access.rs`](../src/access.rs), HTTP —
[`src/http_api/auth.rs`](../src/http_api/auth.rs). Неизвестный MCP-инструмент
запрещён любой роли; новые HTTP routes требуют Admin до явной классификации.
`tools/list` показывает только разрешённые роли инструменты из выбранного
`RAG_TOOLS=spine|full`; вызов инструмента проверяет права повторно.

## Подключение клиентов

- **Native UI:** передай выданный токен через `RAG_HTTP_TOKEN` в окружении
  процесса `rag-mcp-ui`. Этот клиентский параметр не создаёт роль на gateway.
- **Web UI:** открой «Доступ», введи токен и сохрани. Он хранится в
  `sessionStorage` текущей вкладки отдельно для каждого API base; удаление токена
  очищает эту запись. Не размещай секрет в `VITE_*`: эти значения попадают в
  клиентскую сборку.
- **MCP-клиент или stdio-to-HTTP proxy:** настрой заголовок
  `Authorization: Bearer <token>` через поддерживаемый клиентом механизм
  секретов/окружения. Заголовок нужен на каждом HTTP-запросе, включая initialize;
  отдельного входа в серверную MCP-сессию нет. Клиент должен поддерживать
  пользовательский Bearer-заголовок; OAuth-only connector с этой схемой не работает.
- **Реплика:** `RAG_PRIMARY_TOKEN` содержит административный токен primary.
  Worker отправляет его при register/push/pull/ack. Собственные входящие
  `RAG_HTTP_*_TOKEN` реплики настраиваются независимо.

Native и web клиенты отправляют секрет только в Authorization и не следуют
redirects API. Ссылки браузера сами этот заголовок не добавляют: скачивание
source file выполняется через авторизованный запрос web UI.

Проверка чтения, если токен уже безопасно передан в окружение клиента:

```bash
curl --fail-with-body \
  -H "Authorization: Bearer ${RAG_HTTP_TOKEN}" \
  http://127.0.0.1:7432/health
```

Не помещай реальные токены в URL/query, source code, примеры конфигурации в
репозитории, коммиты или логи. Храни их в менеджере секретов либо в приватном
окружении сервиса. Gateway не предоставляет TLS: для передачи за пределами
доверенной локальной машины используй HTTPS через reverse proxy или защищённый
туннель. Настройка `RAG_HTTP_ALLOWED_HOSTS` проверяет Host для REST и MCP, но
не заменяет Bearer или шифрование транспорта.

## Миграция существующего remote gateway

1. До перезапуска выпусти отдельные случайные токены нужных ролей и настрой их
   в приватном окружении единственного gateway. Сохрани правильные `RAG_DB_PATH`
   и другие параметры действующего сервиса.
2. Передай клиентам подходящие credentials. Для реплик настрой
   `RAG_PRIMARY_TOKEN` от Admin primary; проверки готовности тоже должны
   отправлять Bearer после включения auth.
3. Проверь `RAG_HTTP_ALLOW_REMOTE` и точные remote authorities в
   `RAG_HTTP_ALLOWED_HOSTS`, затем перезапусти один gateway. Не запускай второй
   процесс с той же живой DuckDB для проверки конфигурации.
4. Проверь чтение разрешённым токеном, отказ без токена и отказ Write/Read на
   административной операции. Убедись, что клиенты и реплики переподключились.

Прежнего `RAG_HTTP_ALLOW_REMOTE=true` недостаточно: non-loopback без credentials
после обновления не запустится. Если remote доступ не нужен, миграция может
ограничиться переходом на loopback bind. Удаление всех токенов при сохранённом
remote bind не является способом отключить защиту.

Ротация: замени токен роли в приватном окружении gateway и соответствующих
клиентов, затем перезапусти gateway. Одновременно принимается один токен на роль;
периода перекрытия старого и нового нет.

## Ошибки доступа

| Ответ | Значение |
|---|---|
| HTTP `401`, `AUTH_REQUIRED` | Bearer отсутствует или неверен; также отклоняются несколько Authorization headers. |
| HTTP `403`, `FORBIDDEN` | Токен действителен, но роль не разрешает HTTP-операцию. |
| MCP JSON-RPC error с `data.code=FORBIDDEN` | Аутентифицированному клиенту запрещён инструмент; транспортный HTTP-ответ при этом может быть `200`. |
| Tool отсутствует в `tools/list` | Проверь и роль токена, и `RAG_TOOLS`; скрытый инструмент нельзя вызвать напрямую в обход проверки. |

Разрешённый loopback browser preflight `OPTIONS` не требует Bearer и не вызывает
обработчики данных. Обычные data requests после preflight остаются защищены.

Эта инструкция описывает поведение кода. Её добавление не меняет credentials
или конфигурацию уже запущенного сервиса.
