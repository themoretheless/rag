# Проверка знаний и согласование изменений

На главной странице wiki доступны очередь проверки и сохраняемые предложения. Синтез текста остаётся на стороне человека или клиентского агента; сервер не запускает LLM для проверки.

## Рабочий сценарий

1. «Проверить актуальность» показывает статьи с изменёнными или исчезнувшими источниками. Версионные хеши имеют приоритет над legacy timestamps.
2. «Подготовить предложение» фиксирует исходную статью, её ревизию и полный известный набор источников с текстами и хешами. Создавайте предложение **до** генерации нового текста.
3. Введите новый текст, изучите сравнение строк и снимки источников, сохраните предложение. Несохранённый текст дополнительно хранится в сессии вкладки; ошибка браузерного хранения показывается пользователю.
4. После проверки примите предложение либо отклоните его. История решений остаётся доступна.

Принятие проверяет ревизию предложения, ревизию статьи и реальные хеши содержимого источников внутри той же транзакции, которая публикует статью, provenance, индекс, граф, журнал и статус предложения. Изменение или исчезновение источника приводит к HTTP 409. Отсутствовавший источник, появившийся после подготовки, также вызывает конфликт. Повторное принятие не создаёт новую ревизию.

Отсутствующие на момент подготовки источники показаны отдельно. При принятии в source_versions остаются доступные проверенные источники; пользователь должен удалить или исправить неподтверждённые утверждения. Отсутствие источников не считается доказательством достоверности.

## API для клиентского агента

- `GET /v1/wiki-review`: очередь актуальности; роль read.
- `GET /v1/wiki-proposals`: предложения со снимками; роль read.
- `POST /v1/wiki-proposals`: роль write; JSON с action:
  - `{"action":"create","document_id":"..."}` → снимок до генерации.
  - `{"action":"save","id":"...","revision":1,"content":"..."}` → сохранить предложенный текст, получить новую ревизию.
  - `{"action":"accept","id":"...","revision":2}` → принять проверенное предложение.
  - `{"action":"reject","id":"...","revision":2}` → отклонить.

Для генерации используйте `base` и `sources` возвращённого предложения. После конфликта создайте новый снимок и повторно проверьте правки. Не выдавайте новое сохранение за проверку старых источников.

## Редактор wiki

- При вводе `[[` поиск предлагает до восьми страниц из серверного каталога.
- Выбор вставляет `[[slug|title]]`; «Просмотр» открывает материал рядом с текстом.
- Источники из source_versions можно открыть рядом со статьёй.
- Шаблоны решения, инструкции, обзора сервиса и исследования добавляются в конец текста.
- Backlinks показывают сохранённый контекст графовых связей и открываются независимо от загруженной страницы каталога.

## Хранение и границы

Schema 12 добавляет таблицу wiki_proposals. Предложения локальны для конкретного gateway: они не включены в журнал репликации wiki или переносимый Markdown export. Полная резервная копия DuckDB сохраняет таблицу. Принятая wiki-статья реплицируется существующим механизмом.

Очередь пока использует полный обход корпуса, а список предложений загружает снимки целиком. Автоматический polling, масштабирование истории и новые подключаемые источники требуют отдельных ограничений и измерений. Diff показывает общий префикс/суффикс и заменённую середину; он корректен, но не гарантирует минимальное число изменённых строк.

Статьи без известных связей с источниками не покрываются проверкой. Добавление новых источников в предложение и уведомления агенту пока не реализованы. Нативный клиент пока не имеет этого экрана.

Рабочий gateway и рабочая база в рамках этой реализации не обновлялись; браузерная проверка проводилась на отдельной тестовой базе с mock embeddings.

Свойства wiki и сохранённые представления описаны в [KNOWLEDGE_PROPERTIES_AND_FEEDBACK.md](KNOWLEDGE_PROPERTIES_AND_FEEDBACK.md). Там же описан сбор реальных вопросов для оценки поиска.
