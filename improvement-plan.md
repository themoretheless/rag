# План улучшений rag-mcp — gap-анализ против топ-100 open-source RAG

Дата: 2026-09-29
Основа: инвентаризация текущего кода + ландшафт фич из [top-100-rag-oss.md](top-100-rag-oss.md).

## Что уже сильно (не трогаем)

Гибридный поиск BM25+vector с RRF, граф (wikilink + темпоральные kg_facts),
собственный eval (recall@k/MRR/nDCG, LLM-judge, A/B), ревизии с CAS-восстановлением,
проверенные бэкапы, дедупликация, цитаты с char-offsets, MCP-first API (~97 инструментов),
ролевые токены, один бинарь на Rust без Python. По архитектуре eval и audit-логов проект
уже впереди большинства приложений из топ-30.

## Критические разрывы (делают поиск хуже топовых движков)

### 1. Нет реранкинга — приоритет P0
Стандарт продакшна у RAGFlow, Dify, Onyx, Haystack: кросс-энкодер поверх top-20..50
после RRF. У нас только diversity/recency. Это самая большая потеря качества retrieval.
- Добавить `rerank` стадию: провайдеры `ollama`/OpenAI-compatible (BGE-reranker, Jina reranker), локальный ONNX-кросс-энкодер как опция.
- Параметры: `rerank=true`, `rerank_top_n`, fallback при недоступности модели — не ломать поиск.
- Валидировать через существующий eval: recall@k и nDCG до/после на текущих датасетах.

### 2. Парсинг документов — P0
Топовые проекты (RAGFlow/DeepDoc, Docling, MinerU) задали планку: структурный PDF
(заголовки, таблицы, порядок чтения), DOCX/PPTX/XLSX, OCR. У нас PDF только через
внешний Poppler, HTML — грубый tag-strip, офисных форматов нет.
- PDF: заменить/дополнить Poppler на библиотечный парсер (например, `lopdf`/`pdfium` binding или вызов markitdown/Docling как внешний конвертер).
- DOCX/XLSX/PPTX: минимум — извлечение текста с заголовочной структурой (docx-rs, или внешний конвертер как subprocess, по образцу Poppler).
- HTML: заменить tag-strip на readability-подобное извлечение основного контента.
- Таблицы: сохранять в Markdown-виде внутри чанка.

### 3. Нет веб-ингестии — P1
firecrawl/crawl4ai (оба в топ-10) показывают спрос: URL → чистый Markdown → индекс.
- `ingest_url`: fetch + readability → ingest_text-пайплайн, с robots/allowlist и content-hash дедупом.
- Позже: shallow-crawl (список URL со страницы, глубина 1-2).

### 4. Трансформация запросов — P1
`multi_query_search` принимает готовые реврайты от вызывающего; сервер сам не умеет.
HyDE припаркован как P2. У LlamaIndex/kotaemon это встроено.
- `query_rewrite=true`: серверный LLM-реврайт (2-3 варианта) + RRF поверх multi_query.
- HyDE: `hyde_search` — гипотетический ответ → векторный поиск. Оба через существующие LLM-провайдеры, кэшируемые.
- Мерить через eval A/B — не включать по умолчанию без выигрыша.

## Средние разрывы (паритет с рынком)

### 5. Чанкинг — P1
Сейчас char-window + Markdown-заголовки + эвристика для кода.
- Настоящий AST-чанкинг кода через tree-sitter (функции/классы как чанки) — заметный выигрыш для кодовых корпусов.
- `parent_chunk_id` (parent-child retrieval: искать по маленькому чанку, отдавать родителя) — уже предлагался, стандарт у LlamaIndex/RAGFlow.
- Шаблоны чанкинга по типу документа (Paper/Manual/Q&A) — дифференциация RAGFlow, можно взять как конфиг.

### 6. Файловый watcher — P2
Основной backend без watcher (только scheduled sync). pathway/LightRAG показывают инкрементальное обновление в реальном времени.
- `notify`-based watcher на `RAG_INGEST_ROOTS` → debounce → sync_sources. Низкий риск: sync уже транзакционный.

### 7. Токенизатор — P2
`chars/4` для max_context_tokens даёт заметные ошибки на CJK/коде. Подключить tiktoken-rs / tokenizers и калибровать под активную LLM.

### 8. Eval-совместимость — P2
Свой eval функционально сильный, но не читается внешним миром.
- Экспорт метрик в терминах RAG triad (faithfulness, answer relevancy, context precision/recall) и/или адаптер датасетов RAGAS — для сравнимости и CI.

## Крупные ставки (дифференциация, по желанию)

### 9. ANN/VSS — P2, evidence-gated
Точный cosine сейчас укладывается в 134 ms p95 при 100k чанков; порог 300 ms.
При росте корпуса к ~1M чанков — HNSW (hnsw_rs или DuckDB VSS, когда станет
persistence-safe). Держать в ROADMAP как уже решено: только по бенчмарку.

### 10. LLM-извлечение сущностей в граф (GraphRAG-style) — P3
Граф сейчас только по wikilink/тегам. Microsoft GraphRAG/LightRAG показывают ценность
NER + community summaries для глобальных вопросов. Документировано как deliberate
non-goal — пересматривать только при реальном сценарии «вопросов ко всему корпусу».
Если делать: инкрементальное извлечение при ingest, запись в kg_facts, dual-level search.

### 11. Мультимодальность — P3
OCR сканов/изображений, аудио-транскрипция. Дорого, текстовый корпус — основа.
Опциональный внешний конвертер (как Poppler) — приемлемый компромисс.

### 12. Семантический кэш ответов (GPTCache-style) — P3
Кэш LLM-ответов по cosine-похожести запроса. Актуально, только если compile/judge
вызываются часто и дорого.

## Рефакторинг/эксплуатация

### 13. Reembed-миграция — P1
Смена embedding-модели сейчас тяжёлая (uncapped reembed + рестарт, поиск закрыт).
- Фоновый reembed с прогрессом, чанками, без закрытия поиска (dual-index: старые векторы обслуживают поиск, пока новые не готовы; атомарный flip).

### 14. Веб-фронтенды — P2
`web/` — только старый build; живые `web-svelte/` и egui. Удалить или заархивировать `web/`, чтобы не путать.

### 15. FTS reindex discipline — P2
DuckDB FTS не обновляется сам; уже есть dirty-generation markers. Добавить метрику/алерт на устаревший FTS и авто-реиндекс в maintenance loop.

## Дорожная карта (предлагаемый порядок)

| Фаза | Содержание | Эффект |
|---|---|---|
| Фаза 1 | Реранкинг (1) + eval до/после | Максимальный прирост качества поиска за минимальную цену |
| Фаза 2 | Парсинг (2): PDF-библиотека, DOCX, нормальный HTML | Убираем «garbage in» — главный источник плохих ответов |
| Фаза 3 | Веб-ингестия (3) + reembed-миграция (13) | Новый источник данных + убираем операционную боль |
| Фаза 4 | Query rewrite/HyDE (4) + AST-чанкинг кода и parent-child (5) | Качество retrieval второго уровня |
| Фаза 5 | Watcher (6), токенизатор (7), eval-экспорт (8), FTS-алерты (15), зачистка web/ (14) | Полировка и паритет |
| Фаза 6 (опционально) | ANN (9), GraphRAG-NER (10), мультимодальность (11), сем-кэш (12) | По реальной нагрузке |

Каждый пункт с влиянием на retrieval (1, 4, 5) принимать только через существующий
eval A/B — у проекта уже есть инфраструктура, которой нет у большинства топ-100.
